# Полная локальная установка — план реализации

> **Status:** in progress — первая волна модулей; локальная поставка ещё не готова.
> **Owner:** координатор проекта; исполнители — onprem_architecture, ux_implementation, normative_base.
> **Surface:** server, deploy/onprem, public, test, документация и offline-дистрибутив.
> **Updated:** 2026-09-05. **Baseline:** `07498bc`, пилот 0.3.2.

## Что считаем результатом

### Выбор LLM — опция, Codex остаётся базовым режимом

Уточнение владельца от 2026-09-05: локальная установка не заменяет и не удаляет существующий способ подключения Codex.

| Режим | Подключение | Требование |
|---|---|---|
| Codex — по умолчанию | Существующий официальный вход через аккаунт, общий для приложения, без платного API-ключа | Новая установка требует собственной авторизации. Исходники содержат механизм входа, но не сессию, токены или данные владельца проекта. |
| Локальная модель — опционально | Подготовленный внутренний inference-сервер; модель и параметры задаёт администратор установки | Авторизация Codex не требуется для анализа. Локальная ошибка не запускает внешнюю модель автоматически. |

- LOC-01/02: сохранить оба исполнителя и общий процесс primary → review → proposal; модель и провайдер фиксируются для запуска. Ревью и повтор не должны незаметно уходить к другому провайдеру.
- LOC-03: выбор режима на уровне приложения доступен только администратору. Пользователь видит активный режим и место обработки данных. Переключение блокируется при выполняющихся/ожидающих заданиях и незавершённом входе; история и результаты сохраняются.
- Переключение на локальный режим не означает logout Codex и не уничтожает его серверную авторизацию. Возврат использует сохранённую авторизацию, если она ещё действительна; иначе требуется обычный повторный вход. Отдельная явная команда отключения Codex сохраняется.
- В local mode интернет-поиск организации через Codex не запускается скрытно; ручное заполнение карточки остаётся доступным.
- В Git и исходный архив не входят auth.json, токены, пароли, рабочие конфигурации, пользовательские договоры, базы, логи и резервные копии. Только обезличенные примеры и явно синтетические тестовые данные.

Дополнительная приёмка LOC-01…04: чистая установка без авторизации владельца проекта; регрессия текущего Codex-входа; local без Codex-сессии; сохранение серверной сессии при переключении туда и обратно; отказ переключения при занятой очереди; отсутствие внешнего fallback; неизменность старых результатов. Перед публикацией — скан истории Git, проверка состава архива и отсутствия эксплуатационных данных. Автоматический скан не доказывает отсутствие всех возможных секретов.

### Полностью локальный контур

Один сервер организации устанавливается из проверенного комплекта без интернета и выполняет загрузку, первичный анализ, ревью и подготовку правок локальной моделью. Документы и результаты не покидают контур. Наличие HTTP-адаптера или source-архива само по себе не означает готовность локальной установки.

Первая целевая топология: один экземпляр приложения, SQLite, один исполнитель очереди, внутренний inference-сервер. PostgreSQL, Kubernetes, SSO и несколько GPU не входят в обязательный минимум.

### Последовательность

1. **Волна 1 — независимые модули:** local provider/tokenizer, OCR, normative import. Приёмка модулей, согласование API и негативные unit-тесты.
2. **Волна 2 — интеграция:** общий runner, постоянный и временный анализ, подготовка правок, администраторская настройка и offline UX; ограничения регистрации, импорт/активация норм, регрессии Codex.
3. **Волна 3 — поставка и испытания:** закрытая сеть, комплект зависимостей, установка/обновление/откат, backup/restore, реальная модель и OCR, уточнение аппаратных требований по замерам.

## Неизменяемые требования

- REQ-01: два этапа с разными инструкциями; решение ревью по каждому первичному замечанию, серверная проверка схемы и доказательств.
- REQ-02: исходная нумерация пунктов/разделов и ссылки на неё; технические ID не становятся номерами договора.
- REQ-03: PDF, DOC, DOCX, пакетная загрузка и точная дедубликация; оригиналы и старые редакции не меняются.
- REQ-04: разовая проверка без помещения документов/результатов в постоянное хранилище; инфраструктурные копии входят в аудит.
- REQ-05: общий провайдер приложения, простой логин/пароль; текущий официальный Codex-вход сохранён как отдельный режим, без платных API-ключей.
- REQ-06: нет встроенных организаций; локальный режим допускает ручное заполнение, но не незаметный интернет-поиск.
- REQ-07: нет тихой обрезки контекста, облачного fallback и автоматического повышения юридической достоверности нормативной базы.
- REQ-08: никаких секретов, договоров и эксплуатационных конфигураций в публичном Git или архиве; лицензию проекта выбирает владелец отдельно.

Аппаратные рекомендации в архитектуре — предварительные, не измеренная производительность. CPU/RAM/GPU/ОС стенда запрошены у владельца. Без стенда можно завершать код и mock-тесты, но нельзя заявлять промышленную готовность или обещать скорость.

## Учёт результата

Этот план — единственный реестр статусов данной инициативы; архитектура хранит проектные решения, changelog — только выпущенные изменения. При сдаче модуля фиксируются точные файлы, команды и результаты, ограничения и необходимые интеграционные изменения. «Mock passed», «real passed» и «not run» различаются. Завершение задач отражается вместе с соответствующим логическим изменением; выпуск требует отдельного контроля поставки и отката.
