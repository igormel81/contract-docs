# Договоры и риски — пилот 0.1.8

Назначение: внутреннее рабочее место Кастис / ООО «ЗИС» и ООО «Модеус» на `https://igoruan.ru/docs/`.
Это первая реализация, не весь объём согласованной продуктовой спецификации; проектные материалы хранятся отдельно от репозитория исходников.

## Реализовано

- Самостоятельная регистрация по логину/паролю, серверные сессии, выход, смена пароля; аккаунты изолированы.
- Заказчики, договоры и шаблоны; два независимых профиля подрядчиков.
- Пакетная загрузка PDF/DOC/DOCX по кнопке и перетаскиванием; SHA-256 точных исходников, подсказка похожего текста, подтверждение состава и родителя редакции.
- Сохранение оригиналов и неизменяемых комплектов; просмотр извлечённого текста и скачивание исходников.
- Паспорт и рекомендации: два отдельных запуска `codex exec`, разные инструкции, JSON Schema и проверка цитат на сервере. Первый результат не считается прошедшим ревью.
- Один общий вход Codex через официальный device-auth для приложения; API-ключей нет. Подключение настраивает владелец, все пользователи используют общую очередь и лимит. Авторизация root, других приложений и прежние личные авторизации не используются.
- История запусков, сохранение первичного результата при сбое ревью; новая попытка не затирает старую.
- Редактирование и принятие рекомендаций в план правок, JSON-экспорт.
- Постоянные риски, ответственные, мероприятия, статусы с основанием, сигналы и подтверждение инцидентов; автоматического закрытия рисков нет.
- Просмотр двух редакций рядом, подтверждение действующего комплекта, журнал действий.
- Разовая проверка договора с приложениями: без заказчика, карточки, редакций и постоянной истории; паспорт, анализ, независимое ревью, источники и TXT-отчёт.
- Компактный паспорт без дублирующего блока сверху. Ссылки замечаний и рисков показывают исходные пункты/разделы, а не внутренние идентификаторы.
- Кандидаты в риски: замечания завершённого анализа видны во вкладке «Риски» со счётчиком, их можно внести в реестр или отклонить с основанием. Автоматического заноса нет и не будет.
- Ревьюер возвращает решение по каждому замечанию — подтверждено, исправлено, отклонено, — а полный результат собирает сервер. Пропуск замечания считается ошибкой этапа: молчание не проходит за проверку.
- Формулировка правки готовится по запросу для одного пункта, а не для всех замечаний подряд. Запрос идёт вне очереди анализа и отклоняется, пока выполняется запуск.
- Сравнение редакций по пунктам: без изменений, изменён, перенумерован, новый, удалён. Сопоставление по номеру, затем по тексту; это разметка текстовых изменений, а не смысловой разбор.
- `npm run stats` — сводка по запускам: стоимость этапов, что менял ревьюер, сколько замечаний дошло до решения и до риска.
- Текст замечаний для менеджера: короткая сводка или полный список, копирование, TXT и черновик письма. Собирается кодом из сохранённого результата, без обращения к модели.
- Одно меню на шесть разделов: паспорт, анализ, документ, комплект, риски, история. Загрузка файлов, состав новой редакции и список редакций — один раздел «Комплект»: это одна работа. Вторая область — спутник без собственного меню: она показывает то, что парно открытому разделу, чаще всего исходный пункт выбранного замечания или риска. Ссылка на пункт не уводит из раздела. Несохранённые правки рекомендаций остаются в памяти вкладки при переключении разделов, но не переживают перезагрузку страницы или выход.

## Пункты, разделы и источники рисков

Извлечение `structure-v3` сохраняет буквальную нумерацию, а в DOCX также восстанавливает обычные многоуровневые списки из numbering.xml: начало, перезапуск, override и наследование стилей, десятичные, буквенные и римские номера. Естественные абзацы-продолжения объединяются с пунктом. PDF сохраняет номера из текстового слоя и страницы; DOC использует видимые номера antiword. Неподдерживаемые определения, поля Word, таблицы и исправления сопровождаются предупреждениями, отсутствующие номера не придумываются. Это не полное воспроизведение вёрстки Word/PDF; колонки, сложные/связанные списки и спорные границы требуют проверки оригинала.

Идентификаторы fileId/blockId остаются только внутренними ключами API и якорями, не заменяют номера договора в интерфейсе. Агент получает исходные номера и разные инструкции этапов; сервер проверяет дословные цитаты и формирует подписи ссылок по документу. Не найденное условие может не иметь конкретного пункта.

При регистрации риска из замечания сохраняются проверенная цитата, текст пункта, имя и хеш файла, редакция и исходный анализ. Вручную можно выбрать пункт из текущей редакции. Основание риска хранится отдельно в `risk_sources` и не меняется при следующей редакции или повторном чтении документа. Ссылки на чужие договоры/аккаунты отклоняются. У прежних рисков источник восстанавливается из сохранённого анализа, если такая привязка существовала; иначе явно показано отсутствие подтверждённого пункта.

Старые анализы и их снимки не переписываются. Для ранее загруженного файла открыть «Загрузка» → «Текст» → «Обновить структуру», затем запустить новый анализ. Ссылки старых результатов открывают старый снимок, а не новую структуру с совпавшим внутренним ID. В интерфейсе чтения нет технической нарезки и подписей b1/b2.

## Критерии проверки

Сервис рекомендательный: правила формулируют вопросы к переговорам и предложения в интересах подрядчика, а не заключение о соответствии и не проверку на нарушения. Решение принимает сотрудник, спорное условие может быть сознательным выбором компании.

Набор из двенадцати правил принят для пилота 3 сентября 2026 на основе черновика `outputs/rules-draft.md`: условия срабатывания подпроверок перенесены в рабочие формулировки. Развёрнутый файл остаётся источником, при расхождении рабочим считается `server/rules.mjs`.

Десять правил, у каждого своя версия и список «не считать замечанием». Версии хранятся в снимке запуска: после изменения правила прежние анализы не переписываются, а в истории договора видно, какой именно критерий изменился с момента запуска. Критичность определяется типом проблемы — неограниченное обязательство, одностороннее право заказчика, отсутствие существенного условия, — а не величиной процента или суммы: пороги компанией не утверждены.

LAW-01 не входит в покрытие: правило, которое по построению всегда возвращает «нужны данные», не является проверкой. Вместо него сервер добавляет в ограничения каждого результата постоянную оговорку о том, что правовая экспертиза не выполнялась.

Профиль подрядчика передаётся агенту тремя группами: подтверждённое реестром ФНС, заявленное самой компанией и неподтверждённое. Вывод, опирающийся на две последние группы, оформляется как запрос данных. Лицензии и ресурсы связанных юрлиц подрядчику не принадлежат.

Фикстуры `test/rules/<ПРАВИЛО>.json` фиксируют, что каждое правило обязано найти и чего находить не должно. `npm test` проверяет только структуру и полноту набора; фактическое срабатывание проверяется вручную через `npm run rules:eval` на реальном подключении Codex, поэтому обычные тесты остаются детерминированными и офлайн.

## Разовая проверка

Кнопка «Разовая проверка» в боковом меню или `/docs/#quick`: выбрать подрядчика, перетащить PDF/DOC/DOCX либо выбрать несколько файлов, нажать «Проверить пакет». Точные дубли исключаются внутри пакета. Общее подключение Codex и его очередь используются без дополнительного входа.

Оригиналы удаляются сразу после извлечения текста, включая ошибки чтения. Текст, паспорт и результаты двух этапов остаются только в оперативной памяти приложения до одного часа с момента создания пакета. Перезапуск службы или кнопка «Удалить пакет» очищают временную сессию; удаление также останавливает выполняемый анализ. По истечении часа доступ блокируется сразу, фоновая очистка выполняется каждые 30 секунд. Результат можно скачать в TXT; первичный отчёт без завершённого ревью явно помечен. Скачанные пользователем отчёты сервис не удаляет.

Никакие заказчики, договоры, оригиналы, редакции, анализы, риски или журнал действий разовой проверки не записываются в постоянную БД. Обычные данные учётной записи и счётчики ограничения запросов сохраняются. Нет постоянного отслеживания рисков и истории; для этого нужен режим хранилища. Один временный пакет на пользователя, до 12 одновременно в приложении; до 20 файлов, 20 МБ на файл, 100 МБ и 360 000 символов на пакет. Текст не обрезается, превышения блокируются. OCR не подключён.

На VPS `DOCS_RUNTIME=/run/contract-docs` указывает на tmpfs; systemd создаёт закрытый RuntimeDirectory (0700) и удаляет его при остановке службы. Core dumps службы отключены. Локальный запуск без этого параметра использует отдельную временную папку ОС. Каждый временный этап Codex получает отдельный CODEX_HOME/CODEX_SQLITE_HOME, `--ephemeral`, отключённую историю и локальные журналы; рабочая папка очищается после этапа и при отмене. Обратно в общее подключение может попасть только обновлённый файл авторизации, но не тексты или сессии.

Текст передаётся OpenAI через Codex для анализа. Разовый режим не означает Zero Data Retention у провайдера и не меняет условия обработки данных OpenAI. Не загружайте документы, передача которых этому провайдеру не разрешена вашей организацией.

## Ограничения пилота

- OCR и проверенная обновляемая нормативная база **не подключены**. Правовые выводы требуют проверки юристом; LAW-01 выведено из покрытия и остаётся постоянной оговоркой.
- Текст для менеджера выносит условия договора за пределы контролируемого контура: отправку выполняет человек, приложение ничего не отправляет само. Формирование текста и выгрузка JSON записываются в журнал.
- PDF читается по текстовому слою. DOC — antiword; DOCX — ограниченный разбор XML. Изображения, сложная разметка и исправления требуют проверки оригинала. В режиме хранилища оригиналы не преобразуются и не удаляются; при разовой проверке они удаляются после чтения.
- В хранилище: до 20 МБ на файл, 200 МБ на пользователя, 2 ГБ суммарно; не более 50 файлов в комплекте, 360 000 символов на анализ. Превышения блокируются, текст не обрезается. Для разового режима действуют отдельные ограничения выше.
- Нет общего доступа сотрудников и полной матрицы ролей. Новый аккаунт видит только собственные данные, анализ использует общее подключение Codex. Единственное специальное право владельца — управление этим подключением.
- Нет автоматического определения заказчика/предмета до анализа, смыслового diff, Word redline, автоматического сопоставления рисков между редакциями, ручных уточнений паспорта и оценки финансовых потерь.
- Подключение шаблона как эталона конкретного анализа, утверждение правил/шаблонов, отчёт разногласий DOCX и полноценная карта обязательств — следующие этапы.
- В хранилище файлы и очередь, уже переданные на сервер, сохраняются; выбранные, но ещё не загруженные локальные файлы при перезагрузке страницы теряются. Повторная отправка безопасна благодаря хешу. Разовая проверка сохраняет сессию только до указанного срока или перезапуска службы.
- Обработка Codex последовательная. При лимите или ошибке требуется явный повтор. Успешное сохранение авторизации не доказывает доступность модели или наличие лимита.
- Без браузерного подтверждения входа в ChatGPT полноценный AI-сценарий не может быть проверен. Mock-тесты не заменяют проверку реального анализа.

## Среда и запуск

Node.js 22.13+ со встроенным SQLite; AJV 8.20.0. На Linux нужны Python 3, poppler-utils, antiword, bubblewrap. На VPS используется уже установленный Codex CLI 0.152.1.

```sh
npm ci --ignore-scripts
npm run check
npm test
npm start
```

Дополнительно: `npm run rules:eval` — ручной прогон фикстур правил через подключённый Codex (в `npm test` не входит, требует общего входа и расходует лимит); `node test/browser-center.mjs` с установленным puppeteer и `CHROME_BIN` — браузерная проверка компоновки на 1440/768/375 со снимками в `DOCS_UI_SCREENSHOTS`. Годится и системный Chrome: `CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"`. Если прогон замирает на первом же клике, а страница при этом отвечает на `page.evaluate`, дело в самой сборке браузера, а не в приложении.

По умолчанию приложение слушает только `127.0.0.1:3107`. Настройки: `DOCS_ORIGIN`, `DOCS_DATA`, `DOCS_PORT`, `DOCS_CODEX`. Изоляция извлечения включена по умолчанию. Только для локального HTTP-теста можно указать `DOCS_EXTRACT_SANDBOX=off`; HTTPS с этим параметром запрещён.

## Общее подключение Codex

`DOCS_CODEX_ADMIN` — точный логин владельца приложения (после нормализации регистра). На текущем VPS в unit-файле задан `igor`, существующий аккаунт владельца. При другой установке измените это значение на контролируемый вами логин. Если параметр не задан, никто не получает право управления авторизацией автоматически, в том числе первый зарегистрировавшийся пользователь.

Владелец открывает настройки → «Подключить общий Codex» и подтверждает вход в ChatGPT. Одноразовый код и действия подключения/отключения доступны только владельцу; сервер проверяет права независимо от интерфейса. Остальные пользователи видят только общий статус. Вход хранится в `$DOCS_DATA/codex/application/auth.json`, вне исходников, в закрытой папке службы; он переживает перезапуск, выход пользователей из приложения и смену их паролей. Каждый анализ по-прежнему состоит из двух независимых сессий с разными инструкциями; общее подключение не объединяет документы и результаты разных пользователей.

Отключение требует подтверждения, останавливает исполняемый анализ и отменяет очередь всех пользователей, затем удаляет только общий локальный файл авторизации. Готовые и уже сохранённые первичные результаты остаются. Повторное подключение не возобновляет отменённые задания автоматически. Это локальное отключение сервиса, не отзыв всех сессий аккаунта ChatGPT.

При обновлении 0.1.0 → 0.1.1 личные каталоги `$DOCS_DATA/codex/<user-id>` не переносятся и не удаляются; новая версия их не использует. Нужен отдельный подтверждённый вход для приложения. Миграция таблиц и изменение пользовательских паролей не нужны.

Регистрация пока открыта: каждый зарегистрированный пользователь может запускать анализ через общий подключённый аккаунт в пределах ограничений сервиса. Для использования вне доверенной команды требуется отдельное ограничение регистрации/доступа. Проверьте пригодность выбранного плана ChatGPT для вашего внутреннего сценария; сохранённый вход не гарантирует квоту или доступность модели.

## Безопасность и размещение

Служба работает как отдельный пользователь `contract-docs`, не root. Исходники доступны только на чтение. БД и оригиналы находятся в `/var/lib/contract-docs`, доступ 0700. Пароли хешируются scrypt; cookie HttpOnly/SameSite/HTTPS, проверка Origin и специального заголовка для изменений, ограничения частоты. Произвольные пути файлов и внешние URL сервер не принимает.

Извлечение документов выполняется в bubblewrap без сети, с одним исходником и ограничением времени/вывода. Codex получает текст через stdin и отдельную папку каждой сессии; только хранилище авторизации общее для приложения. Shell, браузер, приложения, плагины, hooks и другие инструменты отключены. Сервис не наследует API-ключи из окружения. Сохранённый результат не может напрямую менять БД, состояние рисков или исходники.

Публичный маршрут добавляется только для `igoruan.ru` и `/docs` / `/docs/*`. Главный CV-сайт, `/vector`, webhook, HAProxy и VPN-конфигурация сохраняются. `deploy/route.py` сначала проверяет кандидат Caddy, делает закрытую резервную копию и применяет конфигурацию сигналом SIGUSR1 без перезапуска процесса. Не запускать повторно без осмотра.

Перед публикацией: установить пакеты извлечения, развернуть отдельный release, запустить службу, проверить локально вход/загрузку/права, затем добавить маршрут. Для отката маршрута восстановить сохранённый Caddyfile на VPS и отправить SIGUSR1. Данные приложения при откате не удалять.

Для резервного копирования данных использовать SQLite backup API / согласованный снимок БД вместе с файлами. Авторизации Codex содержат секреты: не включать в незашифрованные переносимые архивы. Автоматический внешний backup и политика хранения ещё не настроены; до реальных договоров согласовать их.

- [Caddy CLI / Signals](https://caddyserver.com/docs/command-line#signals): SIGUSR1 для `caddy run` с конфигурационным файлом.

## Визуальное направление

Спокойное светлое рабочее место для чтения документов в офисе. Product register / Minimalist: две нейтральные поверхности, зелёный акцент только на действиях и состояниях, системный шрифт, тонкие разделители, без декоративных изображений. Плотность 7/10, вариативность 2/10, движение 1/10. Ориентиры: привычная боковая навигация Linear, документ в центре как в Notion, адресные действия у замечаний. Дизайн-навыки использованы для иерархии и последовательного раскрытия деталей, не для выбора маркетингового шаблона.
