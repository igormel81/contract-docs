# Правила работы агентов

Этот файл — единственная обязательная точка входа для агентов во всём репозитории. Системные инструкции и прямое задание пользователя имеют больший приоритет. Не создавайте копии этих правил для отдельных инструментов; локальный `AGENTS.md` допустим только при появлении действительно особых требований подкаталога.

## Перед началом

1. Выполните `git status --short` и не перезаписывайте чужие изменения.
2. Найдите активную инициативу через `plans/README.md` и прочитайте только её план и непосредственно связанные файлы.
3. Не читайте целиком большой `README.md`, архитектуру или changelog, если задача не требует их изменения.
4. До правки сформулируйте границы файлов, критерий приёмки и минимальную проверку.

## Источники истины

| Область | Источник |
|---|---|
| Поведение приложения и API | код и тесты в `server/`, `public/`, `test/` |
| Правила анализа | `server/rules.mjs`; фикстуры — `test/rules/` |
| Схемы результатов модели | `server/schema.mjs` |
| Текущая работа и её статус | соответствующий файл в `plans/` |
| Архитектурные решения и ограничения | соответствующий файл в `specs/` |
| Только уже выпущенные изменения | `changelog/` |
| Команды разработки и обзор продукта | `README.md`, `package.json` |

При расхождении плана и кода сначала установите фактическое состояние тестами и diff, затем исправьте статус плана. Не переносите незавершённую работу в changelog.

## Неизменяемые требования продукта

- Сохраняйте существующие номера пунктов и разделов договора. Технические `fileId` и `blockId` не должны становиться пользовательскими ссылками.
- Каждый вывод и риск по возможности содержит проверенную цитату и ссылку на исходный пункт. Ненайденное условие явно помечается как требующее проверки.
- Анализ двухступенчатый: первичный этап и независимое ревью используют разные инструкции. Первичный результат нельзя выдавать за прошедший ревью.
- Старые редакции, результаты, нормативные снимки и источники рисков не переписываются.
- Codex остаётся базовым режимом приложения; локальная LLM — явная опция администратора. Запрещены скрытая смена провайдера, облачный fallback и тихая обрезка контекста.
- Разовая проверка не помещает договоры и результаты в постоянное хранилище.
- Поддерживаются PDF, DOC и DOCX, пакетная загрузка и точная дедубликация; оригиналы не изменяются.
- Результат является рекомендацией для специалиста, а не заявлением о полноценной юридической экспертизе. Статус `verified` нормативной базе присваивает только назначенный юрист.
- В Git, исходный архив, тестовый вывод и сообщения агентов не попадают реальные договоры, базы, логи, токены, `auth.json`, пароли, ключи и production-конфигурации.

## Экономия лимитов и делегирование

- Не запускайте субагента для чтения статуса, одной очевидной правки или проверки, которую координатор выполнит быстрее.
- Делегируйте только независимые, ограниченные задачи с непересекающимся владением файлами. Обычно достаточно 1–3 агентов.
- Для поиска, профильных тестов, документации и локальных правок предпочитайте доступную быструю экономичную модель, включая Luna. Более дорогую модель используйте только для сквозной архитектуры, безопасности или сложного юридико-технического ревью.
- Передавайте минимальный контекст: цель, разрешённые файлы, инварианты, критерии приёмки, команды проверки и явные нецели. Не передавайте полную историю чата без необходимости.
- Ответ субагента должен содержать только результат, изменённые файлы, выполненные проверки, оставшиеся риски и блокеры. Не заказывайте параллельно одинаковое исследование нескольким агентам.
- Субагенты не делают commit, push, tag, release или deploy, не обращаются к рабочему VPS, не скачивают модели и не используют реальные договоры без отдельного прямого разрешения. Интеграцию и выпуск выполняет координатор.
- В общей рабочей папке заранее закрепляйте файлы за агентом. При пересечении остановите одну из задач, а не объединяйте конкурирующие правки вслепую.

## Изменения

- Делайте минимальный связный патч без попутного рефакторинга.
- Сохраняйте обратную совместимость сохранённых анализов и БД либо добавляйте явную миграцию и тест.
- Для исправления дефекта сначала добавьте или выберите тест, который воспроизводит проблему.
- Не ослабляйте серверную проверку схем, цитат, прав доступа, подписей и digest ради прохождения UI-сценария.
- UI должен сохранять существующий визуальный язык, клавиатурный доступ и рабочую компоновку на 375, 768 и 1440 px.
- Документация описывает только подтверждённое состояние и различает `mock passed`, `real passed` и `not run`.

## Лестница проверок

Запускайте проверки от дешёвых к дорогим и не повторяйте полный прогон у каждого агента.

1. Синтаксис и базовые контракты: `npm run check`.
2. Профильный тест изменённой области: `node --test test/<name>.test.mjs`.
3. После интеграции связного набора — один полный `npm test`, запускаемый координатором.
4. Для UI после профильных тестов — один браузерный прогон на 375/768/1440 и визуальная проверка снимков.
5. `npm run rules:eval`, реальная LLM, русский OCR, GPU и закрытая сеть — только когда задача прямо требует соответствующих финальных ворот. Не выдавайте mock за реальное испытание.
6. При изменении публичной документации — `npm run docs:build`; архив создаётся только после коммита через `npm run source:bundle`.

Если среда не позволяет выполнить обязательную проверку, укажите точную непроверенную границу. Не заменяйте её предположением.

## Git, выпуск и доказательства

- Не очищайте и не откатывайте чужой dirty worktree. Запрещены разрушительные Git-команды без прямого указания пользователя.
- Перед передачей результата выполните `git diff --check`, просмотрите `git status --short` и перечислите фактически запущенные проверки.
- Commit/push выполняются только после зелёного согласованного набора тестов. Deploy дополнительно требует секрет-сканирования, проверенного архива, smoke-теста и понятного отката.
- Changelog обновляется в том же релизном изменении и содержит commit, проверки, ограничения, размещение и rollback evidence; планы отражают незавершённую работу.

## Готовность задачи

Задача завершена, когда реализованы критерии приёмки, профильные тесты проходят, документация не преувеличивает состояние, а координатор получил короткий проверяемый отчёт. Наличие кода без интеграции, реального испытания или требуемого UI считается промежуточным результатом.
